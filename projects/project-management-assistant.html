Part 1

The app: full-stack development

Before any AI, this is a complete multi-user project manager: authentication, role-based access, live collaboration, dashboards. The AI features build on top of it.

Features

Dashboard & calendar

A cross-project overview: a summary chart you can switch between relative size and 100% status mix, a due-date calendar with hover previews, and coming-up and overdue lists.

Projects, members & roles

Create projects, invite members by email, and assign manager, editor or viewer roles. Every role is enforced by the API and reflected in what the UI lets you do.

Project page Task page

Projects & tasks

Status, priority and due dates, with filtering, sorting, pagination and inline editing of every field. The project page shows progress at a glance, and each task page holds the rich-text notes the AI assistant reads.

AI task creation

Describe a task in one line, and the AI fills in the title, status, priority, a suggested due date and a description. The model is asked for strict JSON, which the server parses into form fields, and everything stays editable before you save.

AI rewrite of task content

Turn rough meeting notes into a structured document in one click. The model writes Markdown, and a small server-side parser converts it into the editor's TipTap JSON, so the result is normal editable content.

Live collaboration

Two people on the same task see each other's avatars and which field the other is editing, updated in real time over Socket.IO. Sockets authenticate with the same JWT as the API, and presence tracks every tab a user has open, so closing one tab doesn't make you disappear.

Themes

Light, dark and Solarized themes built on CSS variables. The saved theme is applied before the first render, so there's no flash of the wrong colours.

The AI chat assistant has its own deep dive in Part 2.

Engineering decisions

01

Keep server data in React Query, not React Context

The first version held projects and tasks in React Context, which meant manual refetching, stale data after mutations, and re-renders across the tree. I removed both contexts. Server data now lives in the React Query cache, and the current project comes from the URL, so a page can be refreshed or shared as a link and land in the same state.

Trade-off: a sizeable refactor across hooks and pages. In return, cache settings live in one global config instead of being overridden hook by hook.

02

Define permissions and validation once, for both client and server

The client and server each kept their own copy of the role permissions, and they had drifted apart. The server used POST while the client used post, and the client was missing entries for AI chat and task content. I migrated both apps into a monorepo and moved the permission table and Zod schemas into shared packages. Now a form and its API endpoint validate against the same schema, and each rule exists in exactly one place.

Trade-off: up-front work on the monorepo and ESM/CommonJS packaging. I kept the full history of both original repos with git subtree.

03

Presence at the field level, not just "who's online"

When two people edit the same task, the risky moment is when they're typing in the same field. Each task is a Socket.IO room, and clients broadcast focus and blur events per field, so the UI can show "Bob is editing the description". Sockets authenticate with the same JWT as the REST API. The presence store tracks every tab a user has open, so closing one tab doesn't make you vanish for everyone else.

Trade-off: presence lives in server memory, which is fine for a single instance. Scaling out would need a shared store such as Redis.

04

Measure performance, then fix the biggest cost

I timed the project page's API and found 5 separate count queries (total, todo, in progress, done, filtered). Combining them into one MongoDB $facet aggregation, plus indexes on the task fields that queries filter on, cut the request from ~370 ms to ~181 ms.

On the client, every route, the rich-text editor and the AI panel are lazy-loaded. The AI panel is prefetched in the background once tasks load, so it still opens instantly. DOMContentLoaded went from 354 ms to 192 ms (dev build).

Part 2

The AI assistant: RAG, built and measured

Wiring an LLM to a database is the easy part. The hard part is making answers trustworthy: finding the right passage, not inventing facts, and saying so when the answer isn't in the data. Everything here was driven by measurement.

How it works

When someone edits a task (indexing)

  1. SaveRich-text content is saved as usual
  2. Debounce 15 sThe timer restarts on every save, so only the final version gets embedded
  3. ChunkText is split into overlapping 150-word windows
  4. Embed & indexEach chunk is embedded and indexed for vector and keyword search

When someone asks a question (answering)

  1. Check accessProject membership is verified before any AI call is made
  2. ClassifyRuns in parallel: is this a FACT, LIST or OPEN question?
  3. RetrieveTop chunks from vector search, optionally fused with BM25
  4. AnswerA prompt matched to the question type, streamed back with live progress stages

Implementation & optimization

01

Keep embeddings fresh without paying for every keystroke

The editor auto-saves every few seconds. Re-embedding on every save would waste API calls on text that's about to change anyway. A server-side debouncer keeps one timer per task and restarts it on each save, so only the content that sits unchanged for 15 seconds gets chunked and embedded.

The timers live in memory, so a server restart could lose a pending job and leave the AI answering from outdated text. To catch that, each save marks the task's embedding as stale. If a stale task is opened later, the job is re-queued in the background without slowing down the page.

Trade-off: up to ~15 seconds before new edits are searchable. That was an acceptable price for far fewer embedding calls.

02

Build an evaluation harness before tuning anything

Early on, every prompt tweak "felt" better, and I had no way to tell. So I built a test set: 26 questions over a seeded project, covering dates, numbers, attribution, multi-part answers, summaries and one question with no answer in the data. It has 92 hand-labelled "gold facts", each mapped to the exact chunk that contains it.

A script runs every question against 6 retrieval setups and records what was retrieved and what was answered. I grade the 156 answers by hand, and analyzer scripts turn the results into comparison reports and HTML viewers.

Tracing each wrong answer to its cause gave me six failure types, including:

  • Chunk boundary splits: the right task was found, but the answer's sentence landed in a neighbouring chunk that missed the top 8.
  • Semantic mismatch: "What did Bob work on in February?" is a person + date filter, and vector search can't express that.
  • Metadata hallucination: when retrieval came back thin, the model filled the gaps from the project's task list.

Evidence on GitHub: failure-type analysis · test cases & gold facts · eval scripts

Trade-off: hand-grading is slow. But it turned "seems better" into numbers I could compare between runs, and every decision below rests on it.

03

Make retrieval swappable, and keep a "no retrieval" baseline

I implemented four strategies behind one interface, selectable per request: chunked vector search, one embedding per task, hybrid (vector + BM25 merged with Reciprocal Rank Fusion), and full context, which skips retrieval and puts every task in the prompt. Several chunk sizes can be stored side by side for A/B comparison.

Full context is too expensive to ship at scale, but it's the ceiling: if it gets a question wrong, retrieval isn't the problem. That split separated retrieval failures from generation failures.

One surprising finding: on one question, hybrid and chunked retrieved the same chunks, yet hybrid was consistently right. BM25 only changed their order, and the model anchors on what it reads first.

Trade-off: more code paths and more Atlas indexes. The free tier caps a cluster at 3 search indexes, so I designed the index layout around that limit.

04

Route answers by question type instead of one generic prompt

"When did Stripe go live?" needs one precise fact. "What action items came out of the post-mortem?" needs a complete list. One prompt did both badly. So a small classifier labels each question FACT, LIST or OPEN, and each label gets its own answer rules. For example, FACT answers must quote their evidence or say the answer isn't there.

It's built to never make things worse. The classifier runs in parallel with retrieval, only after the permission check passes. If it fails, the request falls back to the original prompt. When it's unsure, it picks LIST, the safer choice.

05

Stream answers, and fall back between providers without mixing them

DeepSeek is the primary model because it's cheaper, and OpenAI is the fallback. One withFallback helper covers both normal and streaming calls. For streaming, the fallback only fires if DeepSeek fails before the first token. If it fails halfway through an answer, the user gets a clear error instead of a reply stitched together from two different models.

Answers stream over Server-Sent Events, which cuts the perceived wait from the routing trade-off above. The server also sends real stage events ("analysing", "searching", "generating") from actual points in the pipeline, not a fake progress bar.

What I'd do next

  • Metadata filters for person + date questions, the weakest category in my evals.
  • Query rewriting so follow-ups like "and his March work?" resolve before retrieval.
  • Broader automated tests. Vitest is set up on the client, starting with the shared permission rules. The API and the eval grading are next.
  • Deploy it with a seeded demo project so anyone can try it.
