Real estate media delivery platform

After a property shoot, the photography company uploads every photo, video and floor plan in one place. The agent picks what to show, edits the listing page, and shares it with buyers and renters.

Overview

Real estate photography companies have a lot of media to manage for every property (print-quality photos, videos, floor plans and VR tours), and all of it has to reach the agent. Doing that over email and file-sharing links is slow, and it's hard to track what the agent has chosen to publish.

This platform puts the photography company and the agent in one shared workflow.

Architecture

An ASP.NET Core Web API split into separate projects by layer, so each layer can only depend on the ones below it.

Key decisions

01

Build "download all" ZIPs in a temp file, not in memory or straight into the response

Read the reasoning

"Download all" packs every file in a listing case (print-quality photos, videos, floor plans) from Azure Blob Storage into one ZIP. I compared three ways to build it:

  1. In memory (MemoryStream). The simplest option, but the whole ZIP sits in server memory, so memory use grows with every file and every concurrent download.
  2. Straight into the HTTP response, building and sending at the same time. It uses little memory, but there are two problems. First, once the first byte is sent, the 200 OK can't be taken back. If one Blob file fails halfway through, the user gets a broken ZIP that looks like a successful download. Second, .NET 8's ZipArchive only writes synchronously, and ASP.NET Core blocks synchronous writes to the response by default. Turning on AllowSynchronousIO would hide the error, but it brings back the reason it's off: a slow client would tie up a server thread for the whole download.
  3. A temp file on disk (what I chose). The ZIP is built completely on disk first, then sent. Memory holds only small buffers, no matter how big the ZIP gets. If anything fails while building, nothing has been sent yet, so the global exception middleware returns a normal error. ZipArchive's synchronous writes go to local disk, which is fast, and ASP.NET Core then streams the finished file to the client asynchronously. Because the file size is known, the response includes Content-Length, so the browser shows real download progress.

Two details in the implementation: the temp file is opened with FileOptions.DeleteOnClose, so it's removed automatically once the stream closes, even if the request fails, and with FileOptions.Asynchronous for async reads when sending. Entries are stored with no compression, because photos and videos are already compressed and compressing them again only costs CPU.

Trade-off: it needs temporary disk space, and the download only starts once the whole ZIP is built.

02

Give each object the lifetime that matches how it's shared

Read the reasoning

I learned this one from an error: "Cannot consume scoped service from singleton." It comes down to one rule: anything an object depends on must live at least as long as that object. Once I thought about lifetimes that way, I set three levels:

  • Singleton for clients that pool connections: BlobServiceClient, and the MongoDB client inside MongoDbContext. Both are thread-safe and designed to be created once and shared. Creating one per request opens new connections every time and can exhaust them under load, the same trap as new HttpClient() per request.
  • Scoped for EF Core's DbContext and everything built on it. A DbContext isn't thread-safe and tracks changes for a single unit of work, so each request gets its own. Repositories and services are scoped too: a singleton holding a DbContext would keep one alive for the whole app and share it across every request, which is exactly what that error prevents.
  • Per file for streams during a ZIP download. Each Blob download stream and ZIP entry stream is disposed as soon as that file is copied (await using), so only one file is open at a time. ZipArchive is opened with leaveOpen: true: disposing it writes the ZIP's table of contents but keeps the temp file open so it can be sent. ASP.NET Core disposes the temp file after the response, which triggers DeleteOnClose.

Trade-off: the rules constrain the design. Singletons must be thread-safe and can never depend on scoped services, and anything that runs after a request ends has to create its own scope.

03

Keep SQL Server, Blob Storage and MongoDB consistent without a shared transaction

Read the reasoning

One upload or delete touches three systems: SQL Server for records, Blob Storage for files, and MongoDB for audit logs. They can't share a transaction, so if one step succeeds and the next fails, they drift apart. SQL Server is the source of truth, so I ordered each flow so that a failure leaves the less harmful kind of mismatch:

  • Upload: files first, then the database records. If the database write fails, the only leftovers are files nothing points to, which waste some storage. The other order could leave records pointing at files that don't exist, and the front end would show broken media. All records for one upload are saved with a single SaveChanges, so the database never holds half an upload.
  • Delete: soft delete in SQL, keep the file. The record is flagged as deleted and the file stays in Blob Storage, so a mistaken delete can be undone.
  • Audit logs: a known gap. The log is written to MongoDB after SQL has saved. If that write fails, the error reaches the exception middleware, so the user sees a failure even though the change was saved, and may retry and create a duplicate.

Trade-off: ordering the steps this way accepts leftover files in Blob Storage in exchange for never showing users broken data. Those files need cleaning up eventually.

Quality & conventions

  • Every error goes through one exception middleware and returns the same response shape
  • Status codes follow a shared table: 201 for creates, 204 for deletes, 403 vs 401, and so on
  • Dependency injection for every service, and transactions for multi-table writes
  • Conventional commits tied to Jira tickets, e.g. feat(TICKET-123): …

Testing

  • xUnit tests for listing case, media and agent-selection services
  • Moq to fake the database, Blob Storage and auth

What I learned

  • Decoupling with SOLID in practice: interfaces, a generic repository and DI. Every repository and service sits behind an interface and is registered in DI. Services depend on interfaces, not concrete classes (dependency inversion), and each repository interface exposes only what its callers need (interface segregation). Repositories share a generic base: IGenericRepository<T> and GenericRepository<T> hold the common CRUD, and a specific repository like AgentPhotographyCompanyRepository inherits it and adds only its own queries. Swapping an implementation means changing one DI registration, and unit tests can hand in Moq fakes.
  • DTOs for every request and response, never entities. The API contract can change without touching the database model, clients can't set fields they shouldn't (like IsDeleted or a user ID), and internal fields such as password hashes never leak into a response.
  • Rules at three levels: data annotations, Fluent API, FluentValidation. Simple column rules (required, max length) live on the entities as data annotations. Relationships and database-wide behaviour are set with the Fluent API in the DbContext: one-to-one links from User to its Agent and PhotographyCompany profiles, cascade delete turned off everywhere because deletes are soft, and a global query filter that hides IsDeleted rows from every query. Incoming requests are checked separately with FluentValidation on the DTOs.

What I'd do next

  • Bigger downloads: ZIPs are so far tested with MB-sized listings. For multi-GB listings, I'd build the ZIP in Blob Storage and hand out a temporary download link (SAS URL), since App Service has limited local disk.
  • File cleanup: delete an uploaded file straight away if its database write fails, and run a scheduled job that removes files with no record, plus files for records soft-deleted longer than a set period.
  • Reliable audit logs: write audit events into SQL Server in the same transaction as the change (an outbox table), and have a background job copy them to MongoDB, so a MongoDB outage can't lose a log or fail a saved request.
